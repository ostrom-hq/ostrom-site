title: Relayed MCP servers and secrets
description: "Give agents tools without giving them the keys."

Ostrom relays your organization's MCP servers to every agent it launches. The agent connects to Ostrom, never to the
server, so the credentials stay on the Ostrom server, every call is checked against the member's rights and the
organization's argument policies, and every call is journaled.

Two kinds of server are relayed:

- **Remote servers** (`http`, the Streamable HTTP transport), reached over HTTPS at the URL you declare.
- **Hosted commands** (`stdio`), npm or PyPI packages that Ostrom itself runs on its MCP host. Nothing runs on a member's
  workstation or in a session's pod.

## Secrets

A secret is a named value that belongs to the organization (`/api/v1/secrets`). Its value is written once and never read
back: the console and the API show names and metadata only. A server declares the secrets it needs by name, and Ostrom
puts the value in the request or the process environment at the moment of a call. An agent never holds one.

Owners and admins manage the organization's secrets.

## Add a remote server

An owner or an admin declares it with `POST /api/v1/mcp/servers`: a `name`, an HTTPS `url`, the transport `http`, the
`secretNames` it needs, and a `scope`. Ostrom sends the credential with every call, as `Authorization: Bearer <secret>`
unless `credentialHeader` names another header (`X-API-Key`, say). The relay only reaches servers over TLS, and checks the
address it is about to reach.

- **`shared`** (the default): one credential, an organization secret, for everyone.
- **`per-member`**: each member brings their own. An owner or an admin assigns the server to one member and names one of
  that member's personal secrets as `credentialSecret`.

The name is 1 to 64 characters of lowercase letters, digits, dots, underscores and dashes, starting with a letter or a
digit. `servers`, `settings`, `calls`, `usage` and `hosted` are reserved, and so is any name an agent would take for one
of Ostrom's own servers (`ostrom`, `workflow`). Agents see the server as `<prefix>-<name>`, dots turned to underscores,
with the prefix set on the console's **MCP servers** screen (`ostrom` by default).

Who may use a server, and which calls it refuses or holds for a yes, are set per server by owners and admins, with
assignments and argument policies. A server nobody is assigned to is reached by nobody. An existing server's address and
transport never change: to move one, declare a new server.

## Add a hosted command

A hosted command is declared with the `stdio` object of `POST /api/v1/mcp/servers`:

- `launcher` is `npm` or `pypi`;
- `packageName` is the package, pinned exactly: `@scope/name@1.2.3` for npm, `name==1.2.3` for PyPI. A range, a tag, a
  path or a URL is refused;
- `args` are the arguments that follow the package (at most 32 of 512 characters). `${NAME}` in an argument is replaced
  by the secret variable `NAME`, which must be a key of `secretEnv`;
- `env` holds plain variables and `secretEnv` maps a variable name to the name of an organization secret. A secret
  injected into a process is at least 8 characters long, so that scrubbing it never mangles ordinary output.

Running third-party code is an owner's or an admin's decision. A member's own hosted server (a personal server) is
refused with `hosted_not_allowed` unless an administrator turned `memberHostedMcp` on in the MCP settings, which is off
by default. The server needs an MCP host to run any of it (`OSTROM_MCP_HOST_URL` and `OSTROM_MCP_HOST_TOKEN`).

What the host does with it:

- **One process per server**, or per member for a per-member server, started on the first call (or when the member lists
  their servers), stopped after 15 minutes without a call, and never more than 16 at once.
- **No shell, a clean environment.** The host builds the command line itself, under `prlimit`, with an environment made
  from scratch: a minimal `PATH`, `HOME` and `LANG`, the launcher's own settings, and the variables and secrets of the
  declaration. Variable names that could move the registry, the install scripts, the TLS checks or the loader are refused.
- **Frozen at the declaration day.** The package and its dependencies are resolved as they were when the server was
  declared, so a version published later is never taken. For npm, install scripts never run; for PyPI, a package that
  ships no wheel may run its build backend when it is installed.
- **Limits.** At most 512 MiB of memory per process tree, 16 requests at once per process, requests of at most 2 MiB and
  answers of at most 4 MiB per message. More than three failures in ten minutes put the process in backoff for ten
  minutes.
- **Scrubbed.** Every secret value is removed from the answers and from the error output the host keeps.

> [!WARNING]
> Processes share the MCP host's pod and its user. The mitigations are the ones above (only administrators declare them,
> exact versions, npm install scripts off, one cache per process, a host with no database, no key and no cluster access, and
> a network policy), but a malicious package could still read its neighbours' environment. Declare packages you trust.

The package and its version are part of the declaration and never change: to upgrade a package, declare a new server
under another name and assign it again.

## Watch the hosted commands

The console's **MCP servers** screen has a **Hosted commands** section for owners and admins (`GET /api/v1/mcp/hosted`):
one line per process (a shared server once, a per-member server once per member) with its state, its last failure, the
number of starts and failures, the last cold start, the memory, the last exit code and the last 4 KiB of its error
output, read from the host when the page loads. If the host does not answer, the screen says so and shows the states
last recorded.

| State | What it means |
|---|---|
| `idle` | Not running: it starts on the next call |
| `starting` | The host is starting it |
| `ready` | Running and answering |
| `failed` | The last start failed |
| `backoff` | Too many failures: no start for ten minutes, unless restarted |
| `unknown` | A state the host reports that Ostrom does not know |

**Restart** (`POST /api/v1/mcp/hosted/restart`) stops the process and lifts a backoff; the next call starts it again. It
needs, from the console, a sign-in less than five minutes old (a `step_up_required` 403 otherwise; an API token is not
asked), is journaled before the stop as `mcp.stdio.restarted`, answers 404 for a server or member that has no such process,
409 when the instance has no MCP host, and 503 `mcp_host_unavailable` when the host does not answer.

Members see the state and the last failure of their own hosted servers, without the error output, on the same screen and
in `ostrom mcp list`. A state that cannot be read is left out: a server is never hidden from an agent for it.

## Events

A hosted command's state changes reach the organization's event journal (subject `mcp`) and its outgoing webhooks:

| Event | When | `data` |
|---|---|---|
| `mcp.stdio.failed` | A process starts failing (`failed` or `backoff`), once per failure streak: retries and an expired backoff stay in the same streak until a start succeeds | `server`, `memberId` (per-member only), `state`, `failure` |
| `mcp.stdio.recovered` | The process is `ready` again after a failure | the same, `failure` naming what it recovered from |
| `mcp.unreachable` | The state sweep could not reach the MCP host, or the host refused it, while the organization has hosted servers; at most one every ten minutes | `reason`: `unreachable` (no answer) or `refused` (another token or protocol version) |

The subject id is the server's name, followed by `/` and the member's id for a per-member process, and empty for
`mcp.unreachable`. A per-member process's events belong to its member; a shared process's and `mcp.unreachable` belong
to nobody, so only owners and administrators see them in the feed (a webhook receives all of them). No event carries a
secret, an argument or an output. States are swept once a minute, so an event follows its transition by up to a
minute, and a failure that recovers between two sweeps is not seen.

## Troubleshooting

A failed call reaches the agent with one of these causes. The **Hosted commands** section shows the last one of each
process.

| Cause | What it means | What to do |
|---|---|---|
| `start_failed` | The process did not start: the package or version does not exist (or was published after the declaration), it exited early, it has no `tools` capability, or it did not answer `initialize` within 45 seconds | Read the error output in **Hosted commands**; check the package, its arguments and its secrets, then **Restart** |
| `crashed` | The process ended during the call: it exited, passed the memory limit, stopped reading its input, or wrote invalid output | Read the error output; fix the package or its arguments, then **Restart** |
| `timeout` | No answer within the call's deadline. The host keeps the process, and a start in progress goes on for the next call | Try again; look at the cold start time |
| `too_large` | The answer was larger than the limit, or one message passed 4 MiB | Ask for less from the tool |
| `busy` | The process already had 16 requests running for the whole deadline | Try again later |
| `backoff` | More than three failures in ten minutes | Fix the cause, then **Restart** to lift it at once |
| `capacity` | Sixteen processes run and none is idle | Wait, or remove a server nobody uses |
| `protocol` | The process answered a tool request with something that is not MCP | The package is not a working MCP server: check its version and arguments |
| `tool_error` | The process answered the call with an error | It comes from the tool itself: read its message |
| `invalid_spec` | The declaration breaks a launch rule (an inexact version, a reserved variable name, a secret too short) | Declare the server again within the rules above |
| `mcp_host_unavailable` | The MCP host does not answer | Check the host's pod; the states shown are the last recorded |

A remote server that fails reports whether its TLS certificate is not trusted or the server could not be reached, so a
bad certificate is told apart from an outage.
